# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`orochi` is a single Rust binary: an adaptive scheduler that picks an **agent × model × reasoning level × session strategy** for a coding task, drives the chosen CLI agent over ACP (Agent Client Protocol) v1 stdio, evaluates the result locally, and learns from the recorded outcome. It can also expose *itself* as an ACP agent (`orochi serve`).

Rust 1.96.0 is pinned in `rust-toolchain.toml`; edition 2024. `Cargo.lock` is committed and every command uses `--locked`.

## Commands

```sh
mise install && mise run check             # every check CI runs, CLI and desktop crate; `mise tasks` lists the rest
cargo build --locked                       # debug binary (examples/demo.py expects target/debug/orochi)
cargo build --release --locked
cargo fmt --all -- --check
cargo clippy --locked --all-targets -- -D warnings   # warnings are errors in CI
cargo test --locked                        # requires python3 on PATH
```

Tests live only in `tests/*.rs` (no `#[cfg(test)]` modules in `src/`), so target them per file/name:

```sh
cargo test --test cli_e2e
cargo test --test adaptive ewma_reacts_to_recent_drift_and_scales_token_cost_to_task_size
python3 -m unittest discover -s tests -p test_quota_terminal.py   # also run by tests/adaptive.rs
```

End-to-end smoke without any account: `cargo build --locked && python3 examples/demo.py`.

CI (`.github/workflows/ci.yml`) runs on pushes to `main` and on pull requests — not on every branch push — with dependencies cached: fmt / clippy / test on ubuntu + macOS through `mise.toml` (the same Rust, Node and Python as `mise install` gives locally), the desktop crate's clippy and tests (`desktop:lint`, `desktop:test`, which build the sidecar first), a Windows clippy of the CLI and the Windows launcher test. No account, network LLM call, or API billing is needed for any test.

**Keep the loop fast.** Waiting is what slows the work, so: run what the change touches locally (`cargo test --test <file> <name>`, or `mise run quick` — fmt, clippy and every test but the pty-driven `cli_e2e`, ~2½ minutes), push to `main` (`.githooks/pre-push`, enabled by `mise run setup`, runs fmt and clippy), and **do not wait on CI**: carry on and look at the run when it has finished. A red `main` is still fixed before anything else lands on it — it was red for nine days once, and every push after it hid behind that red. `desktop/src-tauri` is outside the workspace, so a root `cargo` command never sees it; `mise run check` does. Code under `#[cfg(unix)]` is built for Windows only on CI, so compile its non-Unix side in your head.

## Execution pipeline

`cli::execute` → `scheduler::run_with_events` is the spine; read those two in order before changing behavior.

1. **Quota refresh** (optional, `quota.refresh_before_run`) — `quota_sources::refresh` shells out to read-only native CLI probes (`codex app-server`, Claude/Antigravity `/usage` via the embedded `src/quota_terminal.py` PTY reader) and persists snapshots.
2. **Profile** — `router::profiler::profile` turns the raw task string + repo into a `TaskDescriptor` (task type, language, complexity, scope, ambiguity, capability needs). Purely local heuristics: keyword matching, so a request phrased outside its vocabulary lands on `implementation`/`Normal`. `router::classifier::refine` then asks an ACP agent to classify the task itself and merges the reply in one direction only — it may raise complexity and add a capability need, never lower or clear one. It runs **by default** (`classifier.enabled`), without `agent` trying every enabled, non-`routing_only` agent in configured order within one agent's worth of time, because sending the request to an agent that would run the work anyway puts the text where it was already going. Any failure keeps the heuristic; a cached reply (salted hash of the task) skips the call. Nothing that has no choice left to make may start an agent to ask: a dry run, a read-only seat, and a route pinned to both an agent and a model all keep the heuristic label.
3. **Discover** — `discovery::inspect`/`prepare` resolve each configured agent to a launch command (native CLI, existing ACP command, or an auto-installed adapter under `<data>/adapters/`), then `acp::Client::start_with_model` connects, creates a throwaway session and enumerates models/reasoning/modes. Runs up to 4 agents concurrently.
4. **Score** — `router::scorer::candidates` expands every (agent, model, reasoning, mode) tuple, applies provider policy + hard constraints + quota availability + `scheduler.required_success`, and sorts by `expected_cost`. It is scored at `ScoringContext::difficulty` where the seat is being asked for a part of the task rather than the whole of it, and at the task's own complexity otherwise. The reasoning level and its price both come from `effort::Ladder`, and a capability requirement is a gate only where some agent in the field claims to meet it.
5. **Advise** (optional) — `router::advisory::advise` may consult a router, a frontier "judge", or a 2-round council. Every adviser is an `[[agents]]` entry (optionally `routing_only`) driven over ACP by `router::adviser::Session`: fresh session in an empty temp dir, permissions denied, council round two reusing the seat's session; without `model`, the adviser model is scored from the agent's models by policy at a per-role difficulty (router simple, council normal, frontier complex). Adviser rate/auth/unavailable failures update that agent's runtime cooldown. Its pick only *reorders* candidates that already passed every constraint.
6. **Select** — `learning::select` applies the EWMA/bandit strategy over the surviving list.
7. **Execute** — `acp::Client::configure` + `prompt`, streaming assistant output to stdout and routing/diagnostics to stderr.
8. **Evaluate** — `evaluator::evaluate` runs auto-detected or configured checks (`CI=true`, no stdin) and `evaluator::outcome` labels the run.
9. **Record** — `storage::Store` writes a `RunRecord` to SQLite; failures update `RuntimeState` cooldowns and the loop retries with a fresh `TaskEnvelope` up to `scheduler.max_attempts`.

`gateway.rs` (`orochi serve`), `chat.rs` (`orochi` on a terminal / `orochi chat`) and `collaboration/` (`orochi collaborate`, independent ACP sessions in copied workspaces) all re-enter this same scheduler rather than duplicating routing logic.

Non-obvious module notes:

- `types.rs` holds every cross-module struct. `RunRecord` is stored in SQLite as a JSON blob, so records written by older versions must still deserialize — new optional fields need `#[serde(default)]`.
- `acp.rs` is the only place that speaks the protocol. ACP configuration is **model-dependent**: `discover()` re-reads the `thought_level`/`mode` selectors *after* switching to each model, and supports both modern `configOptions` selectors and the legacy `models` / `session/set_model` shape.
- `effort.rs` is the effort axis in whatever words the agent uses for it, and the one place that reads it. ACP's `thought_level` values are the agent's own and often its server's (`codex-acp` builds the option from the app-server's `supportedReasoningEfforts`, `claude-agent-acp` from the SDK's `supportedEffortLevels` plus a `default` row), so a policy naming `high` cannot be the only way to ask for more thought. Words are placed on five rungs by what they say, spelling normalized (`x-high` = `xhigh`); an unrecognised word is placed between its recognised neighbours in the order the agent advertised them, and where nothing is recognised the advertised order is taken as ascending — measured on both installed adapters. `ProviderPolicy::reasoning` reads a policy's list for a complexity as an ordered set of *rungs* (literal match first, so a canonical vocabulary is unchanged; then the same rungs in the agent's words; then the nearest rung, a tie going to the dearer level), and `scorer` prices the chosen level from **the same ladder**. That single reading is the point: the choice and the price were separately wrong and cancelled out, so the axis silently stopped moving and no test failed.
- `chat/` decides how much machinery a message needs: `Session::steps` profiles it and splits complex or architectural work into design → implement (→ review) phases, each routed on its own in its own session and peer, handing its reply on; a failed implementation adds a review, and only a review answering `VERDICT: fix` adds one more pass. A message needing a capability (`image`, `browser`, `web`) the conversation's agent lacks runs as a one-off guest turn on a capable agent (clearing `--agent`), and the conversation keeps its own agent, told afterwards what happened. `scorer` also prices an agent another peer is running 1.4× higher (`ScoringContext::busy` from `mailbox::busy_agents`), so concurrent runs spread over accounts instead of racing for one.
- `chat/term.rs` owns the one screen the pinned input and the transcript share: transcript text is written at a tracked (row, column) above the input, so anything that changes the pinned height must free (and clear) the rows it no longer covers and scroll the transcript when it grows — and nothing may write into a half-written row. `tests/test_chat_terminal.py` (driven from `tests/cli_e2e.rs`, rendering the pty output through `tests/screen.py`) is the only test that can see those mistakes.
- `chat/mod.rs` classifies each turn **once** (`Session::profile`) and that one descriptor decides the escalation, the phase split and the routing — it travels into the scheduler as `RunOptions::descriptor` so the scheduler does not ask again about text the console rewrote, and a read-only seat never classifies the prompt Orochi wrote for it. When the design phase ends with a `{"parts": …}` division that lets something run side by side (`collaboration::plan::with_parts`), the console offers to run the rest as a collaboration, showing the order, and only on a terminal: it is the one escalation that starts several agents at once and writes back, so it is the one thing that asks first. The division is held back from the transcript while it streams (`Withhold`) and stripped from the handover. Typing `/` lists matching commands above the input, Up/Down select and Tab/Enter take one.
- `chat/`: `mod.rs` is the session (key loop, queued messages, commands, approval modes, the mailbox `Feed` and the per-turn `Screen`); `term.rs` owns the terminal — raw-mode key decoding, the pinned input line with its attachment rows and status row (a DECSTBM scroll region keeps the transcript in the terminal's own scrollback), and the restore on exit. Each message is one `scheduler::run_turn` with `RunOptions.interactive`, which keeps the scheduler off stderr and reports `acp::Progress` events instead (route, unavailable agents, checks, attempt results; `acp.rs` adds tool calls with their `rawInput` detail and diffs, plans and thinking), sends the text as typed on the first attempt, skips evaluation when `context::tree_fingerprint` is unchanged, and never retries a turn the agent finished. Keys typed during a turn edit the same input line: Enter queues the message, Esc and Ctrl-C raise SIGINT (the queue is still sent next), Up takes the queue back into the input, Shift-Tab cycles the agent's own session modes (`Continuation::modes`) or Orochi's ask/always/never. Key behavior follows Claude Code, not Orochi's own invention: at an idle prompt Esc never exits and twice shelves the draft into history, Ctrl-C clears then exits, Ctrl-D deletes forward or exits on a second press within 800 ms; a permission No (and Esc) stops the turn; the team question after a design is a plan-approval dialog whose Esc keeps the design. Look the behavior up before changing it. Attachments (`types::Attachment`) come from pasted paths and `@path`, and `acp::Client::prompt_with` sends images inline, text as embedded resources, and anything else as a resource link, honoring the agent's prompt capabilities. `run_turn` reports the recorded session (`Continuation`); later messages pin that agent/model and pass `resume` when the agent advertised `session/load`, otherwise a bounded in-memory transcript goes into the task text. A session is also a **thread** in `activity.sqlite3` (`chat::Recorded`): one user message is one turn, each seat and phase is a seat row under it, `/new` starts another thread, and `--continue` picks the last one back up.
- `router/classifier.rs` also answers **which model the work is for**, because it is the only stage that can: it reads the task, and the stages that see the models (`advisory`) are deliberately never shown the task. `classifier::catalog` renders each provider's `ModelRule` — `use_for`, which is the **provider's own account** of what the model is for and never Orochi's opinion of it (`policies/*.json` cites where each line came from), or `describe()`'s line generated from the tier and the price where no one has written one — for the providers of configured agents only, never the `*` fallback, and the reply's `suited` names one. It is the same shape as `prefer` and bound by the same rule: sanitized to a name fragment, applied after every gate, reordering the capable field and opening nothing. **This is a deliberate widening of the classifier's exception, not an oversight**: two models of one tier with the same prior and the same price still differ in what they are good at, and no number in the policy can say which. The catalog is part of what a cached answer was answered for, so it is in the cache key — a policy update asks again.
- `router/classifier.rs`: reuses `adviser::Session` (fresh session, empty temp dir, permissions denied) at `Complexity::Simple`, so the cheapest model clearing the policy floor is picked. **Asking is a whole extra ACP session and costs like one** (2026-09-20: 37,630 tokens on Claude against 23,800 on Codex for the same question, mostly system prompt and cache reads), so the session is made **lean** (`classifier.lean`, on): `Selection::lean` carries the instruction and `discovery::lean` says it in the agent's own words from `[agents.lean]` (`LeanConfig`: `meta` templated into `_meta` on `session/new`, `env` onto the launch with `{instruction_file}`; unset, `LeanConfig::known` by command name — `claude-agent-acp`, `codex-acp`, `gemini`; ACP itself has no field for a system prompt, so any other agent needs its words written in) — measured 2026-10-15 at 815 tokens against 43,854 on Claude (`docs/real-validation-20261015.md`). What each answer cost and took is recorded as a `classification` run — `purpose != "execution"`, so `learning` never reads it — and `classifier::agents` asks the **fastest** answerer first (`storage::advice_latency`, median wall time with the session start, refusals excluded), an agent nobody has timed yet going ahead of the timed ones, and `adviser::choose` takes the agent's model measured fastest (`Selection::timed`, `storage::advice_latency_models`) over the scorer's cheapest once one has been; an agent in cooldown is not started, so a spent subscription hands the question to the next. `classifier::worth_asking` then weighs that price against what work like this has cost here (`storage::typical_tokens`, median of recent executions in the stratum, else of recent executions at large) and keeps the heuristic when asking would take more than `classifier.max_cost_share` (0.25) of it; with nothing measured yet it asks, since asking is how both costs become known. A cached answer is free and is always used. A reply naming a label outside `classifier::TASK_TYPES` is discarded rather than stored — an invented label would silently split the `storage::history` strata an agent/model's EWMA is keyed by. Raising complexity is not free downstream: `roles::seats` seats a second read-only agent for `Complex`/`Extreme` or structural work, which is another whole session, so `roles::worth_seating` holds it back where work like this has measured smaller than `roles.min_work_tokens` (60,000) and the console says so rather than quietly seating one fewer.
- `scorer` separates **what the model is asked for** from what the task is: `ScoringContext::difficulty` picks the success prior and the reasoning level, the descriptor keeps the task's complexity, and only the descriptor reaches the record — so the learning strata are never split by which phase a run happened to be. A chat phase that carries out a settled plan (`Phase::asks_less`) is asked for one step less (`Complexity::eased`, floored at Normal); deciding is where the capability is needed. `ModelRule::price_premium` is the other half: it says how much more a token costs than `relative_tokens` already assumes, defaults to neutral so only a model whose price departs from its tier needs one (Anthropic: `fable` at 2.5, Claude Fable 5.1 at $10/MTok against Claude Opus 5.5's $4), and multiplies the **cost** and never the token prediction, which the EWMA learns from and `calibrate` compares against. Anthropic's own guidance is that most workloads start on the cheaper frontier model and that **tuning effort is usually a better lever than switching models** — which is what `difficulty` is, and why the price premium and `suited` only decide what is left after it.
- `scorer` prices **what a session costs before it does anything** as part of the work: `storage::session_floor` takes the smallest tenth of recent executions on that (agent, model), counted by `Usage::weighted()` — nearly all system prompt and cache reads, which is exactly why counting them raw ranked a model measured on cache-heavy sessions below one that was not — and it opens `initial_tokens`, so `expected_tokens` is a real token figure and everything that budgets against it (adviser seats, `calibrate`) reads real tokens. `CostFeatures::session_tokens` carries the same number so `resource_cost` can leave it out of the cache discount: a cache hit saves re-reading the work, not the prompt the seat opens with. Changing what the prior is made of would otherwise poison the EWMA, which learns `measured / predicted` — so `Prediction::prior_basis` names the recipe (`learning::PRIOR_BASIS`) and a run predicted another way trains success and latency but not tokens. The heuristic size prior (`estimated_context + 1500 × scope`) is a factor common to every candidate, so on its own it cannot tilt the choice; the floor is per seat and can. A model nobody has run falls back to what that **agent's** sessions have cost, taken at its cheapest end — the policy prices `haiku` and `luna` identically (both `small`, 0.65) and they measured 6.3× apart on the same-sized task, so the tier is the wrong thing to fall back to; another agent's sessions say nothing about this one. With neither measured it contributes 0.0, so an unmeasured store ranks exactly as before. Records written before the field existed deserialize without it.
- `learning.tier_pooling` (off by default) starts a model with no history of its own from what other models of the same provider and policy tier did on the same task type, complexity, reasoning and mode (`storage::tier_runs`, `learning::estimate_evidence`). Tier is derived from the model ID at read time, so no stored record changes; `unknown` is never pooled. Replay reads tiers from the bundled policy, not the installed one, so a replay result does not move when policies are updated.
- `activity.rs` + `activity/recorder.rs` is the conversation store a desktop client reads (`docs/desktop-app-design.md`): projects → threads → turns → seats → attempts → items → patches, plus prompts, controls, the mailbox's room and a trigger-fed `changes` feed a reader in another process follows after `PRAGMA data_version` moves. The client reads **only** the `v_*` views; `orochi threads` reads the same ones from a terminal, which is what keeps them honest. `recorder::Tee` puts the store in the path of `ExecutionEvent` without changing what the stream delivers, on a task of its own. Three rules learned the hard way: **one connection per process** behind a mutex (`activity::Shared`) — separate connections only contend, `busy_timeout` *sleeps*, and `sqlite3_close` of a WAL connection deadlocked concurrent seats; the recorder locks **once per event** and hands the guard down, because a guard in a `match` scrutinee lives for the whole match; and any consumer that drains with `try_recv` after its future resolves must finish the tee first or lose the end of the reply.
- `chat/host.rs` (`orochi host --thread <id>`, hidden) **is** the console: it calls `chat::run_with` with a `Keyboard::channel()` it fills from the store, so a queued turn is `Key::Queued` (a message carrying the row it already is, which `open_turn` claims instead of writing another) and a control is the key or command the same request is at a terminal — `interrupt`/`stop` → `Key::Interrupt`, `new`/`reroute` → the command, `set_mode` → `Key::ShiftTab`. It had a loop of its own once and it drifted: a message that seated two agents in a terminal ran alone in the window. Dropping the sender ends the session, which is how a host leaves when it has been idle. It alone leaves permission questions open (`recorder::Answerer::Store`), and with that answerer the recorder sends the question **nowhere else** — a watcher that cannot answer would refuse it the moment its unused sender dropped. `orochi threads new/send/interrupt/stop` are the rows a client writes.
- `chat/background.rs`: helpers a console lead starts with `start_agent` (`docs/supervision-design.md` §4). Only the lead's session is offered the tool: the console holds a `mailbox::delegate` guard for the lead's peer hint during its turn, `register_session` marks that `SessionPeer::delegate`, and its mailbox server gets a `delegate` argument. The request is an `agent_requests` row the console decides on its mail tick (gates: a writing lead, `roles::MAX_SEATS`, `worth_seating`) and answers once. A helper is a `read_only` seat owned by `chat::Session`, not by the turn: polled from both the idle loop and the turn loop, no workspace lock, and `RunOptions::background` gives it `interrupt::never()` so Esc stops only the lead. Its reply is its result; results that end while a turn runs come back as **one** completion turn (`Message::from_helpers`, `turns.origin = 'background'`), routed by the descriptor of the turn that asked and never writing `feedback`. A helper the user stopped only rides along with the next message. Read-only seats' `execute`/`other` requests are asked of the user (`acp.rs`, whatever the approval mode) through one queue (`chat::Ask`); edits stay refused at the source.
- `chat/manager.rs` + `merge.rs` (`docs/manager-design.md`): the console lead is also the conversation's **manager**, with five more mailbox tools offered only to a session marked `SessionPeer::manager` (`mailbox::delegate(hint, manager)`, a `manager` argument after `delegate`): `set_plan` (kept in `threads.management`, shown by `/work`), `list_work`, `stop_agent`, `merge_trial`, `apply_merge`. Every one is an `agent_requests` row with a `kind` and `payload`, decided in `chat::decide_request` on the same mail tick as `start_agent`, answered as JSON in `reason`. **The lead never merges a worktree itself.** `merge::trial` snapshots both trees (`workspaces::snapshot`, the private-index commit factored out of `Workspaces::create`) and runs `git merge-tree --write-tree --merge-base=<launch snapshot>` (Git ≥ 2.40, refused below it: an older base would be the wrong one), checks out the result as a worktree under `.orochi/sessions/<key>/trials/`, and the console runs the project's checks there; `overlap` is the paths both sides changed, the one thing a clean merge cannot vouch for. `merge::apply` takes only a `Clean` trial, re-snapshots the tree and refuses one that moved (`Stale`) — `Manager::run_apply` then tries once more on the tree as it is now, checks again, and writes only a clean passing result — writes through `collaboration::workspace::commit` under the exclusive repository lock, which is `try_lock`, so applies run from the **idle loop only** (`Manager::approved`), never while a turn holds the tree — and **before** the lead is woken, with a wake held while an apply runs and closed input (`Session::team_working`) keeping the console up while a trial, an apply or an unreturned report is outstanding: measured 2026-10-16 (`docs/real-validation-20261016.md`), a Codex lead polls `list_work` inside one long turn and asks for the apply there, and without this the apply raced the exit. HEAD, branch and index are never touched; an applied trial closes the helper's worktree (through the manifest) and its own, and `merge::sweep_trials` goes with `sweep_workspaces`, so no worktree outlives the conversation — the rule `workspaces.rs` set the same day. Who approves: `manager.apply = "ask"` (default) asks the user — an `Ask` with `apply: Some(lines)` in the console, a `prompts` row of kind `apply` under a host, declined outright with nobody to ask — and `"auto"` applies a clean trial whose real checks passed on the lead's word. Between turns the lead's name is held in the room by `mailbox::Inbox` (`Manager::hold_inbox` at the end of `execute`, released before the next session registers), read on the mail tick: a helper's message wakes the lead after `MAIL_HOLD` (60 s), at most `WAKES_PER_HELPER` (3) times per helper, going back with trial and apply reports through `completion_message` (`turns.origin` = `'merge'` / `'mail'`, never `feedback`). `Session::restore` reads `threads.continuation` (now actually read: a host or `--continue` resumes the session, or rebuilds the bounded transcript from `items` for an agent without `session/load`), the plan and the `merges` rows, and a fresh session gets `Manager::standing` — the plan, the team, the trials — above its task. Trials are recorded whole as JSON in `merges` (`v_merges`), content, never telemetry. A helper's worktree is a row too (`workspaces`, 2026-10-16): opened in `grant` with its seat, closed by `finish`, the sweep, an apply (`how = "applied"`) or `orochi workspaces prune` (by path, since prune knows no thread), each with `workspaces::Closed` as written; `v_team` joins each to its seat and latest trial, and `Activity::team` is what the desktop's **Work** pane and `orochi threads team <id>` both draw, so a row the window cannot draw is a view that is missing something.
- `workspaces.rs`: the worktrees a conversation opens for its writing helpers (`start_agent` with `write`), each a detached worktree under `.orochi/sessions/<key>/` from a snapshot commit of the tree at launch, and the rule that **none outlives the conversation**. The lead closes one with the mailbox's `finish_workspace` (`Finish::Merge` three-way file by file through `collaboration::workspace::{merge_text, commit}`, all or nothing, as uncommitted edits; `Finish::Pr` replays `base..head` onto the current HEAD on `<branch_prefix><name>`, pushes and runs `gh`; `Finish::Discard`), and whatever did not land is a `<name>.patch` beside the manifest — a patch is small and is not a worktree. `close_all` is the sweep (`chat::Session::sweep_workspaces` at the end, `/new`, and a resumed conversation), `prune` (`orochi workspaces prune`) the same for session directories nobody `hold`s (a `live` lock each conversation takes at its first worktree, `Env::live`). A `finish` request rides the `agent_requests` table as `kind='finish'` and is answered `started` on success, because that CHECK predates closing. The lead stays in the user's tree. `/worktrees off` refuses writing helpers for one conversation; `[workspaces]` holds the defaults. `collaborate` keeps its copies. `setup` puts `gh` in because of this.
- `pane.rs`: inside an agent host's terminal pane (Orca: `ORCA_PANE_KEY`), the console reports its state and seats with `OSC 9999` from `View::report`, never the prompt or a reply; every launch (`acp.rs`, quota probes) gets the host's hook variables emptied so the CLIs Orochi opens do not each claim the pane. `[console] host_status = false` turns the report off.
- `sandbox.rs` + `sandbox/ops.rs` (`orochi sandbox`, `docs/sandbox-design.md`): a project may run its agents and checks in an Incus instance of its own (Docker inside by nesting), reached over `limactl shell … incus` or a local `incus` client. The tree is mounted **at its own absolute path**, so nothing sent to an agent is translated, and `scheduler::discover_agents` swaps `discovery::prepare` for `Placement::launch` (the agent resolved from the image via `discovery::inside`) while routing advisers stay here. A launch marked `AgentConfig::sandboxed` gets no mailbox server, no mailbox prompt note and no stdio MCP server, since those are this machine's executables. `tests/sandbox.rs` drives it through `tests/fixtures/fake_incus.py`, which runs `exec`'d commands locally. Measured on a real VM (`docs/real-validation-20260930-2.md`), and each of these was a bug there: `incus` reads a non-terminal stdin as YAML, so scripts go in as files and never through `bash -s`; `incus exec --user --group` gives no supplementary groups (the Docker socket carries the user's own group); `incus exec` leaves the process running when its client dies, so every command starts through the image's `sbx-run`, which kills its process group, and a check is held by an open stdin (`SBX_HOLD=1`). **Nothing may change the Mac's system configuration or ask for root** (the user's instruction, 2026-10-01): services are reached through the VM's `*.localhost` gateway (`sandbox/gateway.py`, forwarded by Lima) or `focus`, never a route, a resolver file or a LaunchDaemon. The VM stops itself when unused (`sandbox/idle.py`, a timer inside it) — *used* means a live process carrying `OROCHI_SANDBOX` (so everything Orochi runs inside must carry it, and `sbx-run` must never kill what an agent leaves behind: that is the agent still working), an Incus operation, or a connection — and `ops::ensure_vm` starts it again. Agents inside are signed in with this machine's sign-in (`sandbox/auth.rs`): files kept in step, never single-file mounts (a CLI's rename-over-save fails on one); secrets through `/dev/shm/orochi-env-<agent>` (0600), never `--env` on a command line; a recipe per agent cites that CLI's own docs. `Mode::Runner` puts the agent here and the runtime there: `agent_inside()` decides whether a launch is wrapped, `sandboxed()` whether a sandbox is readied and checks run in it; the agent gets `sandbox/runner.rs`'s MCP server and a note. `ops::ensure_vm`: call it before anything that needs Incus, and never from something that only looks (`status`, `view::sandboxes`), or looking would keep the VM up.
- `opencode` is a preset (`opencode acp`, the CLI is its own ACP server) and **one agent in front of many upstreams**: a model ID carries its upstream as a prefix (`opencode/…` the gateway, `lmstudio/…`/`ollama/…`/`llama.cpp/…` this machine, `anthropic/…` a key), so `policies/opencode.json` matches on the prefix (`local` and `free` tiers, premiums 0.1 / 0.2, priors that fall under `required_success` from `complex` up), `classify_error` makes every OpenCode failure `model_scoped` (a spent free model must not cool down the local one), and `setup::opencode_has_provider` counts a provider written into `~/.config/opencode/opencode.json` as a sign-in. No lean config (whether an agent `prompt` replaces the system prompt is undocumented) and no quota probe. Measured 2026-10-16 (`docs/real-validation-20261016-2.md`): a 27B LM Studio model finished a small task in 2 min 51 s; its one `usage_update` per turn leaves what the total covers unknown.
- `roster.rs` (`orochi roster`, the window's Agents screen): `[[agents]] models` is the **roster**, case-insensitive fragments of advertised model IDs (`policy::matches`), a hard gate in `scorer::candidates` right after quota — `AgentConfig::admits` — that an explicit `--model` bypasses. `discovery::remember` keeps what every full discovery enumerated in `<data>/discovered.json` (a run pinned to one model does not write it), which is what `roster show`, the window and a proposal choose from. `roster::suggest` asks the classifier's answerers (`classifier::answerers`, whatever `classifier.enabled`) through `classifier::consult_as` (an isolated lean session, recorded under purpose `roster`) with `SUGGEST` and a content-free list plus what is remembered; `parse` drops any model ID the agent did not advertise and `apply` writes the rosters into the config (`Config::save` rewrites the file whole, as the window does) and the preferences into memory as Orochi-written lines — the user said a proposal is saved as the decision and adjusted after, never previewed by default. The console's `/roster [set …|suggest]` is the same (`chat::Session::roster_command`, `run_roster` held for the loop like `/mcp`); `adopt` writes the file through `Options::config_path` and swaps the session's `&Config` for a leaked edited one (a few per session), and it applies only when an agent is next chosen, since a conversation under way keeps its pinned session (`Continuation`). `avoid` is the classifier's mirror of `prefer` (`TaskDescriptor::avoided`, ÷0.8 in the scorer), and `orochi memory --add` writes a user line (`Memory::add`, unmarked, never expires; said again, an auto line becomes the user's). Measured 2026-10-16: Codex proposed a roster for four agents in 4.2 s and 15,552 tokens.
- `benchmark.rs` (`orochi benchmark`, `benchmark-tune`) replays paired measured outcomes offline; it never contacts an agent and never writes to the operational DB.
- `setup.rs` (`orochi setup`, the desktop's first-launch dialog): what this machine has of what Orochi needs, and putting in what it lacks without touching the system. Everything Orochi routes to runs on Node.js, and a window opened from Finder has no shell `PATH`, so it found none of it: `setup::search_path` is the `PATH` everything Orochi starts is looked up on — `<data>/toolchain/bin`, `<data>/toolchain/node/current/bin`, the process's own, the login shell's (asked once, `-ilc`, only where `SHLVL` is unset), then `~/.local/bin`, `/opt/homebrew/bin`, `/usr/local/bin`, `/usr/bin`, `/bin` — and `discovery::effective_path` reads it where the agent has no `env.PATH` of its own, putting it on the launch so a bridge's `#!/usr/bin/env node` resolves. `setup::run` writes the config file if absent, Node.js (the newest of `NODE_MAJOR` from `index.json`, the archive checked against `SHASUMS256.txt` before `tar` touches it, `current` a symlink swapped by rename; `OROCHI_NODE_DIST` points a test at a local server), the CLIs asked for (`PACKAGES`: Claude and Codex as the vendor's npm package, `--ignore-scripts`, `@latest`, linked into `toolchain/bin`; Antigravity as `install_antigravity`, the ACP server zip the ACP registry lists with its SHA-256 pinned in `ANTIGRAVITY_BUILDS` and run in place through a wrapper, plus the `agy` CLI from its install script's manifest with the manifest's SHA-512 checked — Gemini CLI is not offered, Antigravity being its successor), then the adapters through `discovery::prepare`, and with `--sandbox` Lima from its GitHub release (`LIMA_VERSION` pinned, `SHA256SUMS` checked, `toolchain/lima/current`, `limactl` linked into `toolchain/bin`) followed by `sandbox::setup::run` — the same `orochi init` — on a blocking thread. `register_data` lets a lookup given no data dir (`discovery::locate`, which the sandbox code resolves `limactl` through) still see the toolchain. `status_with(…, keychain)` is what the window reads: a sign-in is the files and variables `sandbox::auth::recipe` names plus Claude Code's credentials file or keychain item (attributes only, never `-w`); tests pass `keychain = false`. `run` decides its steps before the first starts and reports them through `setup::Progress` (`<data>/setup/progress.json`, rewritten on every change, `job` from `OROCHI_JOB` which `jobs::start` sets so a window can tell this run's from the last one's); each step is also a line on stdout. The desktop runs the same command as `sandbox::jobs::Request::Prepare`, draws the steps with the one under way, their times and a count, keeps the log behind a toggle, and `jobs::cancel` stops the job's whole process group and writes its exit as 130; signing in opens Terminal (`login_command`), since every CLI's login takes a browser and a keyboard. `tests/setup.rs` drives the binary with `env_clear` against a `python3 -m http.server` nodejs.org and a fake `npm`.
- `process.rs`: every ACP agent is launched as `orochi --internal-supervise <lease> <cmd>…` (dispatched in `main.rs` before clap). The supervisor leads the process group, records the agent and observed descendants as (pid, start time) leases under `<data>/processes/`, and kills them if its owner dies; `cli::execute` enables this and reaps leases whose owner is gone. Library callers that never call `process::enable` (e.g. `tests/adaptive.rs`) spawn agents directly.
- `interrupt.rs`: every SIGINT is counted once for the process (`interrupt::listen`, started in `cli::execute`). A `ctrl_c()` future only hears an interrupt that arrives while it waits, so runs take `interrupt::mark()` when they begin and wait on `Since::wait()`, which also completes for an interrupt that came while nothing was waiting (between two attempts, during a merge).
- `memory.rs` is captured with no call of its own: the classifier already reads every request, and its reply may carry up to two `remember` items (repo scope unless the user says it holds for every project), each shown as one `remembered:` line when kept. The note opens every **fresh** agent session — `scheduler` where the prompt is finalised (so chat, one-shot, seats and `serve`), and `collaboration/turn.rs` for participants — and is skipped on `resume`, since that session heard it when it began. Items Orochi wrote carry `<!-- auto seen:N last:T -->`; heard once they expire after 90 days, twice or more after 180, and the user's own unmarked lines never expire, are never replaced and are injected first. Budgets: `memory.user_chars` 1500, `memory.repo_chars` 2500. A console session with two or more messages is looked back over once at its end (`classifier::distill`, Esc skips): only what the user said, kept in memory across `/new` in `chat::Session::said`, never the agents' replies. The classifier also reads, from what is remembered, which agent or model the user wants for this kind of work and returns it as `prefer` — a name fragment of `[a-z0-9._-]`, at most 64 characters, so it cannot carry the user's words into the classification cache (whose key includes the memory listing). `scorer` multiplies a matching candidate's cost by 0.8 after every gate; it never brings a gated candidate back. Designed in `docs/personalization-design.md`.
- `mailbox::prompt_note_for` asks peers to claim a named part of the work with `set_status` *before* changing anything and to leave what others claimed alone, and to hand what a peer is waiting on (a decision they will build on, an interface they will call) over as soon as it holds rather than at the end. It only matters between separate Orochi processes: the repository lock is exclusive unless `scheduler.shared_workspace` is set, and a chat's second seat cannot write at all.
- `mailbox.rs`: one peer per **agent session** (normal runs, `collaborate` and chat phases, not `serve`), so agents inside one process reach each other too; `mailbox::join` only activates the process and `register_session` names each session (`--peer-name` is the prefix). Peers are scoped to the repository's git common dir so worktrees share a channel. `acp.rs` attaches `orochi --internal-mailbox …` (a hand-rolled stdio MCP server, dispatched in `main.rs`) to every non-adviser `session/new`; the scheduler and collaboration prompts prepend `mailbox::prompt_note()`. Messages live in `<data>/mailbox.sqlite3` with a retention window, never in telemetry. `scheduler.shared_workspace` turns the repository lock into a shared lock; applying a collaboration result stays exclusive. `busy_agents(except)` counts every seat but the named one — including this process's own other seats — so the scorer steers them to different accounts. A session registers its route only once it is set up, so a route is also **claimed** (`mailbox::claim`) at the moment of choice, with nothing awaited in between; the seats of one console turn additionally take their places in `mailbox::Order` (lead first) through `RunOptions::place` — a place is taken only once the seat has chosen **and** joined the mailbox, or a seat could start before the lead is there and find nobody to talk to — while their discoveries run side by side.
- `mcp.rs` is every MCP server a session gets that is not the mailbox: `[[mcp.servers]]`, the target repository's own `.mcp.json` (`mcp.trust_repository`, **on**), and the ones an ACP client passed to `orochi serve` (merged into that run's `Config` by `gateway.rs`, a configured name keeping its own definition). One `check` reads all three sources, so `orochi-mailbox`, a relative command and a plaintext URL to anything but localhost are refused wherever they are written; a repository file that fails it is reported, never fatal. `${VAR}` / `${VAR:-default}` expand in a configured server's `env`/`headers` and in every field of a repository's; an unset variable leaves that server out naming it rather than starting it with a hole, and in a **repository** entry's remote `url`/`headers` the credentials in `mcp::WITHHELD` read as empty (Claude Code's list plus every other agent's own), because otherwise a project file could have an agent post the agent's key to a server the file names. **Repository servers are approved as Claude Code 2.1.278 approves them** (its wording, options, default and Esc were read from the installed binary, `~/.local/share/claude/versions/<v>`): `chat::Session::review_repository_servers` asks at startup and before any turn, only with a terminal, "Continue without" focused and Esc meaning it, several at once as a checklist; the answer goes to `<data>/mcp/choices.json` keyed by repository id (never into the repository), approved entries by a **digest of the definition as written** so a rewritten entry is asked about again (Claude Code approves by name — a deliberate difference). `mcp::servers` gives a session everything but the rejected: a run nobody can be asked in (one-shot, `serve`, `collaborate`, a headless host) loads undecided ones as Claude Code's `-p` does, and says so once per repository per process (`mcp::once`); the console never lets one reach a turn undecided. `collaborate` reads file and choices from `report.root`, not the seat's copy, whose path is another repository id. `acp::Client` settles the list once from the agent's `mcpCapabilities` (stdio always, `http`/`sse` only where advertised — measured: claude-agent-acp both, codex-acp `http` only) and keeps the mailbox first; what an agent could not take is reported per agent by the scheduler, beside the agents that could not start. A stdio command is resolved through `discovery::locate`, because ACP asks for an absolute path. Advisers and the classifier (`start_isolated`) get none, and a listing (`scheduler::discover`) starts none.
- `mcp/oauth.rs`: **Orochi is the OAuth client, not the agent it routes to** — it holds the token and hands every session the authorized server, so one sign-in covers whichever CLI runs the work, including the CLIs that cannot sign in at all. The flow follows the MCP authorization specification **2025-11-25** to the letter, because a real provider's shape is what exposed each gap: the `401`'s `resource_metadata` or the RFC 9728 well-known places in order; authorization server metadata in the specified order (issuer with a path: RFC 8414 insertion, OIDC insertion, OIDC **appending**) with no default endpoints; **refuse** a server whose metadata lacks S256 in `code_challenge_methods_supported`; `oauth_client_id` before dynamic registration; the challenge's `scope` before `scopes_supported`; PKCE S256, exact `127.0.0.1` loopback redirect, `state` checked on the socket **and** on a pasted address, `resource` in both requests. The client sends `orochi/<version>` as its user agent — some CDNs answer an unnamed or scripted one with something other than their 401. Tokens go through `oauth::Vault`: the macOS keychain by default (service `orochi-mcp`, one item per server, account = data-dir digest + name, written through `security -i` on stdin because argv is visible to `ps` — its line buffer is 4 KiB, measured, so a larger item falls back to argv as Claude Code does, and what was written is read back since `security -i` exits 0 on a failed command), else `<data>/mcp/credentials.json` (`0600`); a file token moves to the keychain on first read. **Tests always use `Vault::file` and `cli_e2e`'s `Workspace` sets `mcp.keychain = false`: no test may touch the keychain of the machine it runs on.** `oauth::authorize` refreshes **before** the run puts the token in the server's headers rather than letting the agent meet a `401`; a header the user configured is never replaced. `/mcp` in the console and `orochi mcp [login|logout|reset-project-choices]` are the same thing; `chat::Session::mcp` holds the request for the loop to run, because `dispatch` is sync and this is the one command that needs the network and a browser. `--no-browser` is not a nicety — over SSH the browser is on another machine and **nothing** reaches the loopback socket, so `Pending` splits `wait` (the socket) from `pasted` (the address by hand) and `redeem`, and the console offers both at once. `tests/mcp_oauth.rs` drives the whole flow against `tests/fixtures/mock_oauth.py`, whose switches each break one specification rule; live results are `docs/real-validation-20260922.md`.
- `router/roles.rs` + `chat/mod.rs`: a chat turn derives its seats from the task rather than from a fixed pairing, and `worth_seating` then asks whether the second one can pay for itself — it is another session beside the first, so it roughly doubles the turn however small the work turns out to be, and a bare session is most of what small work costs at all. The measure is `storage::typical_tokens` against `roles.min_work_tokens`; an unmeasured store and a team the user asked for outright are never gated. Structural, long-horizon or complex work seats a second, read-only agent beside the one doing it; a request that asks the agents to work together seats as many as it asks for (`TaskDescriptor::seats`, capped by `roles::MAX_SEATS`), each a different perspective from `roles::PANEL`, and a request that only asks them to talk (`task_type == "discussion"`) seats nobody who may write. Every seat runs concurrently under the one workspace lock, in the user's own tree, and they talk over the mailbox. The second seat runs with `RunOptions { read_only: true, verify: false }` — `acp.rs` refuses it every permission request whose `toolCall.kind` is not read/search/fetch/think, and only the lead's turn runs the evaluator. Its own output stays out of the transcript; what it has to say reaches the user as mailbox messages.
- `collaboration/plan.rs`: derives the team from the `TaskDescriptor` when `collaborate` is given no `--plan`, so the deep path stops needing a hand-written one. Counts come from complexity and whether the work is structural; implementers are additionally capped by the number of separate top-level areas the task touches (its `candidate_files`, or the repository's own directories when it named none) — a second implementer inside one directory races the first rather than halving the work. `--dry-run` prints the derived plan as a plan file, so it can be saved, edited and passed back to `--plan`.
- `collaboration/graph.rs`: `Plan::parts` (optional) is the work in order. Orochi's own deterministic gate refuses a list it cannot order, serializes parts that may write the same place (overlapping or absent `paths`), fuses straight chains into one session, and caps a wave at the number of implementer seats; `Plan::steps` turns the waves into `Step::Wave`/`Step::Join`. Parts come from `--plan`, from the first coordinator turn (accepted once, only if something runs side by side), or from the console's design phase. Parts are never gated; a mid-graph merge conflict gets an `untangle` resolution turn that must clear the markers before the next wave copies the result.
- `collaboration/`: `mod.rs` holds the plan, the derived step list (turn groups, merge, discussion rounds, apply) and the resumable `report.json`; `turn.rs` builds prompts, parses trailing JSON (management state, `{"messages": …}`), and runs a turn group concurrently with per-member failover; `workspace.rs` copies, three-way merges (`git merge-file` outside any repo) and commits with stale-write checks; `apply.rs` merges parallel implementers and applies a verified result to the user's tree. Step numbering for single-implementer plans without discussion must stay identical to older reports.

## Invariants (tests assert these — don't regress them)

- **Memory is the user's text, so it lives beside telemetry, never in it, and only Orochi writes it.** `memory.rs` keeps `<data>/memory/USER.md` and `<data>/memory/repos/<repository_id>/MEMORY.md` as plain Markdown. A `MEMORY.md` inside the target repository is never read, no agent gets a tool that writes memory (agent output follows the repository's content), and routing advisers never see it — only the classifier is shown the current repository's listing, so it can say "again" instead of adding a duplicate. Its `remember` / `reinforce` / `replaces` fields are `skip_serializing`, so the classification cache still holds labels only. A repository's notes never reach another repository's prompts. Tests in `tests/core.rs` (`mod memory`) and `a_remembered_note_opens_each_fresh_session_once` pin all of this.
- **A classified failure reports its kind, not the text it was read from.** Bridges wrap provider errors in a generic `-32603`, and the nested `data.details` that `agents::classify_error` reads carries provider request IDs (`tests/adaptive.rs`, `nested_acp_rate_limit_details_are_classified_without_exposing_them`). Only an `ErrorKind::Other` — where the kind says nothing a user can act on — puts that cause in the message, on one line, capped, control characters gone and escapes made visible. `RunRecord` stores `kind.key()` and never the message.
- **Telemetry is content-free; content lives in one file the user can bound or delete.** Task text, conversation, source, diffs, agent stderr and check output never reach `telemetry.sqlite3` — byte-level tests pin this (`tests/core.rs`, `tests/mailbox.rs`). They live in `activity.sqlite3` (`activity.rs`), which is `0600`, `secure_delete`, retained `activity.retention_days` (pinned threads exempt), and absent entirely with `activity.enabled = false`. The link between the files points one way: `attempts.run_id` names a telemetry run, and telemetry never names a thread, so deleting a conversation leaves learning untouched. The router/judge/council payload is classification attributes + at most 12 opaque candidate summaries — no task text, filenames or repo paths (`router_payload_excludes_task_text_and_filenames`). The classifier (`[classifier]`, on by default) is the **one** adviser shown the task text, because it cannot classify without it; it still persists nothing, keying its cache by a salted hash (`classifier_sees_the_task_but_caches_only_a_hash_of_it`). Telemetry's repository identity is a salted hash; `activity.sqlite3` holds the repository *path*, because a sidebar has to show it. Nothing in either file is ever transmitted: no adviser or agent reads them, and the one exception is a thread replaying its **own** earlier turns to its **own** next agent.
- **`end_turn` alone is not success.** `Outcome::PartialSuccess` means unverified or diff-only; only real check passes yield `Success`. Rate-limited/auth/unavailable and mid-run config-switch runs never label learning (`learning::label`); partial and cancelled runs label it only through a weak `feedback` signal, never as verified outcomes (see below).
- **Usage is nullable, never zeroed or estimated, and what a run is *reported* as is not what it is *ranked* by.** `Usage::total()` must not double-count reasoning inside output or cache inside input, and it stays the reported figure: `orochi runs`, `v_runs` and `v_route_stats` show what was actually spent. `Usage::weighted()` is the ranked one — a cache read is a tenth of a fresh input token, a write is dearer than the input it stores, and output is dearest, so a run that is 93% cache reads (measured, 2026-09-22) is not priced as if it were 93% fresh input. Everything that compares one seat against another, or one run's size against another's, reads `weighted()` — the seat floor, the measured side the EWMA and `calibrate` compare predictions against, `typical_tokens` and `advice_cost` — and a record with no cache breakdown reads as its total, so an old record is never guessed into a different number than the same run recorded today. `roles.min_work_tokens` moved with them, 60,000 → 16,000 at the measured 3.73× ratio. `classifier.max_cost_share` did not have to: asking costs what a cold session costs whoever answers (24,262 weighted on `codex`, 20,441 on `haiku`, nearly all of it uncached system prompt), and what was wrong was never the threshold but what the share was taken against — `worth_asking` weighs it against **this** task's `size_prior`, not only against what work of its kind has cost, because the stratum cannot tell a line from a library and measured that is the whole difference (0.114 against 0.348 where the stratum alone read 0.346 against 0.342). A `typical` stratum still decides on its own where it has samples of its own: the point of stratifying is that small work is not classified, or seated twice, because other work here is big. **What a reported total covers is the adapter's choice and the adapters disagree** — `claude-agent-acp` accumulates the turn, `codex-acp` reports `tokenUsage.last`, one model request (1.10.0 and 1.13.1, read 2026-09-25; measured here, Codex executions came out cheaper than a single-request classification on the same seat) — so `Usage::requests` records how many `usage_update` notifications the turn produced. It is never part of a total and nothing is estimated from it: reconstructing the turn would mean inventing the cache/output split. Until `codex-acp` reports totals, Codex token figures are a lower bound and the two agents' counts are not comparable (`docs/real-validation-20260925.md`).
- **A provider is a name, and the set is open.** `types::Provider` is a lowercase ASCII name of at most 24 characters held inline (so it stays `Copy`) and serialized as the plain string it always was — stored records and the generated SQL columns read back unchanged. A `Registry` holds one policy per provider and any number of providers; `Registry::get` falls back to `ProviderPolicy::generic` (the `*`-row priors every bundled policy already applies to a model it does not recognise, canonical rungs, no cache discount, version 0), so an agent from a vendor nobody wrote a policy for is routable rather than having to claim to be one of three — which would file its runs in that vendor's strata, price them by that vendor's tiers and read its errors for that vendor's phrases. An unknown provider's rate-limit wording is read against every provider's phrases, because each of them means a spent account whoever says it.
- **What a usage payload is reporting is read from the payload.** Anthropic's native `input_tokens` excludes cache reads and writes; the fold-in keys on `cache_read_input_tokens` / `cache_creation_input_tokens`, Anthropic's own spelling and nobody else's, never on the configured provider — an agent driving Claude through a bridge configured as anything else was undercounting its input, which since `weighted()` became the ranking basis is a model that looks cheaper than it is.
- **A capability ACP does not advertise is a gate only when somebody claims it.** Browsing, web access and image generation are nowhere in the schema (`promptCapabilities.image` is whether an image may be *sent to* the agent, not whether one may be asked of it). They come from `[[agents]]` flags plus the agent's own `_meta["orochi.dev/capabilities"]` on `initialize`; where no agent in the field claims one, `scorer::candidates` drops the requirement and records why on every candidate instead of emptying the field, and `chat::Session::capable` keeps the turn rather than handing it to a capable agent that does not exist. A preset claims only what its CLI was read to have.
- **`model == "*"` in `runtime` means agent/account-wide.** A rate limit without an explicit `data.scope = "model"` applies to the whole agent; model-scoped failures must not blanket-disable an agent.
- **A verified outcome is never relabeled; an unverified one is labeled only weakly, once.** `RunRecord::feedback` (what the user did next in the console: `continued` 0.2, `rerouted` 0.3 — uncalibrated heuristics; an interruption alone labels nothing, since stopping a turn may mean the user forgot to say something as easily as the agent went astray, and only `/reroute` after it counts against the route) is the only part of a record written after the run, via `Store::feedback`, first signal only, prediction untouched. `learning::label` uses it only for `PartialSuccess` and `Cancelled`; weight enters as `decay^w`, so weight 1 is the unweighted update. `calibrate` reports weak signals apart from the verified numbers. `/new`, quitting and messages queued while the agent was working are not verdicts.
- **Predictions are frozen before execution.** `RunRecord::prediction` is what calibration compares against; never rewrite it after the fact.
- **The target repository is never trusted.** Config is never auto-loaded from the repo; relative `PATH` entries are skipped when resolving executables; adapter installs are pinned-version, install-scripts-disabled, into Orochi's own cache. The **one** exception, at the user's explicit instruction (2026-09-21), is the MCP servers a repository names in its `.mcp.json`, which `mcp.trust_repository` reads by default because a repository that ships one ships it for the agent working there. It stays an exception and not a precedent: every entry passes `mcp::check`, the console asks before using one (as Claude Code does) and a rewritten entry is asked about again, a run nobody can ask in says what came from the file, the file can never make an agent send the agent's own credentials anywhere (`mcp::WITHHELD`), and nothing else is ever read from the repository as configuration.
- **No helper worktree outlives its conversation, and nothing in one is lost or merged unasked.** `workspaces::close` removes the worktree whatever `how` was and keeps what did not land as a patch; the end of a console session, `/new`, a resumed thread and `orochi workspaces prune` close what is still open as patches, never as merges. `tests/workspaces.rs` and `writable_helpers_work_in_their_own_worktrees_which_the_lead_closes_and_the_end_sweeps` pin this.
- **`collaborate` leaves the user's working tree alone unless `--apply` is given, and applies only a result whose real checks passed.** Writes are staged and re-verified against the merge input; a tree edited during conflict resolution blocks instead of being overwritten.
- **Constraints bound every "smart" layer.** Router/judge/council/bandit may only choose among candidates that already passed quota, policy, capability and `required_success` gates, and are additionally capped by `max_cost_ratio` (1.25×) and a resource-fraction budget.

## Conventions

- Config structs use `#[serde(default, deny_unknown_fields)]`, so a new field needs a `Default` impl entry and usually a check in `Config::validate`. `orochi config show` redacts `agent.env` values.
- Code comments are English and rare — they exist to record a decision ("never auto-run a relative PATH entry…"), not to narrate. Match that density.
- `.orochi/` is gitignored local scratch (implementation backups, live-E2E artifacts, downloaded tooling) — not source; ignore it when searching.
- Exit codes: `0` completed, `1` execution/eval/config error, `2` CLI usage error, `130` interrupted or permission denied.

Path-scoped rules live in `.claude/rules/` and load when the matching files are opened: `tests.md` (test harness), `policies.md` (policy JSON + scoring), `docs.md` (English user-facing docs).
